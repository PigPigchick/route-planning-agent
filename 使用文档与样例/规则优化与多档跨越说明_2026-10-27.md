# 协议征询函规则优化与多档跨越使用说明

在协议事项中点“编辑”。公路跨越和河道航道类型显示“跨越明细”，一行对应一档跨越；点“＋ 新增跨越”继续填写，点“删除本行”删除误填的行。保存前的修改是临时资料，取消或关闭窗口不会保存。每份协议支持 1–50 行，每行缺项单独列出；数字由程序原样填入表格，不让大模型计算。

可选“征询主题”只填主题，例如“紫金段优化调整路径方案”，不重复工程名称。未填写时按协议类型和征询轮次自动生成标题。接地极、铁路、地震及军事协调均有独立类型；新增类型是根据样例整理的开发模板，实际必填要点及附件要求仍需业务核对。

旧版 `facts` 单档资料兼容。明确传入 `crossings` 后，以各行参数为准；行内只允许继承通用设施名称和坐标基准，杆塔与数值不会从第一行自动复制。公路多档接口例子：

```json
{
  "id": "AGR-ROAD-01",
  "unit": "模拟公路管理单位（仅测试）",
  "type": "highway",
  "scope": "NA1—NA3",
  "points": "请研究线路跨越方案及后续协调要求，并函复。",
  "round": "first",
  "status": "未发函",
  "facts": {},
  "crossings": [
    {"facilityName":"模拟高速","spanStart":"NA1","spanEnd":"NA2","angleDeg":78,"spanLengthM":168,"horizontalDistanceM":47.34,"clearanceM":29,"chainage":"跨越高速匝道"},
    {"facilityName":"模拟高速","spanStart":"NA2","spanEnd":"NA3","angleDeg":80,"spanLengthM":688,"horizontalDistanceM":78.05,"clearanceM":27.5,"chainage":"K24+750m"}
  ],
  "attachments": []
}
```

此段是单条协议对象，放入现有输入 JSON 的 `agreements` 数组；不是独立任务请求。工程、路径、发函资料与实际附件仍须按原接口提供。河道每行填写 `facilityName / spanStart / spanEnd / coordinateSystem`。铁路的 `facts.facilityName` 填实际铁路设施名称。

标题、专项参数表、附件编号与落款由程序生成。工程概况、路径、征询事项和历史意见作为完整保护段落；模型只接收类型、轮次和占位符结构，原工程资料、原模板文字及来源留在本机。保护段落不得重复或套上另一层“现就……征询”句式。模型仍使用设置中保存的同一配置，未改模型和 Key。

模型输出通过结构和事实引用检查后才采用。结构校验失败最多自动修正一次；第二次仍失败会显示原因并阻止导出，鉴权或网络失败不盲目重复，也不退回模板冒充模型结果。可在任务生成记录中追溯使用模型、提示词版本和各次检查结果。

资料缺失仍须补充，不能用模型推断真实收函单位、坐标、净空或附件。修改跨越参数、事项等正文事实会标记“正文待重写”；点击“重新起草正文”才使用新规则生成，历史正文不会自动覆盖。日期和附件更新沿用原流程，不调用模型。旧任务保留原模板版本；新任务自动采用升级后的有效模板。

Word 已取消按工程名称强行换行；技术表保留每行数据，表头跨页重复，签名与联系资料保持同页。输出采用统一函件版式，尚不等同于复刻样例的红头、印章和所有历史版面。
